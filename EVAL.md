# EVAL — method, results, limitations

Reproduce everything: `make eval` (or `.\scripts\eval.ps1`, or `cd backend && python -m lvda.evaluation all`, or the
"Run again" buttons on the *Evaluation* page). Each run writes `backend/eval/results/{verifier,agent}-latest.{md,json}`
and stores a row in `app.eval_runs`. CI runs the same command on every PR and attaches the reports.

The agent evaluation runs first: the first attempts it logs to `app.agent_logs` become source (b) of the verifier set.

**Everything that involves an LLM below is a mock.** Read those numbers as tests of the pipeline and the harness, not
as model quality.

## 1. Verifier on labelled SQL (real, deterministic)

**Dataset** (`lvda/evaluation.py::build_verifier_cases`):

| Source | How it is built | Label |
|---|---|---|
| (a) Mutations | Mutate each canonical metric SQL: drop a filter, change a filter value, use `payment_value`, join a child table, drop DISTINCT, SUM→AVG, count `customer_id`, filter on delivery date; plus 8 generic cases (join on zip prefix, PII leak, deprecated table, unknown column/table) | Injected rule |
| (b) Agent log | First SQL the agent wrote for each benchmark question, taken from `app.agent_logs` | Mistakes the mock injected (`mock_llm.MISTAKE_RULES`) |
| Correct | Canonical SQL; with the correct time filter; split by state, month, payment type (with the first-installment filter) | No error |

**Results** (latest run, default rule settings):

| Measure | Result |
|---|---|
| Broken SQL caught | 142/142 (100%) — (a) 60/60, (b) 82/82 |
| False alarms on correct SQL | 0/60 (0%) |
| Check latency | p50 11.9 ms · p95 17.4 ms · no LLM call |

Source (b) grows as the agent log grows, so the total drifts by a few cases between runs.

Per rule: V01 2/2 · V02 27/27 · V03 44/44 · V04 11/11 · V05 8/8 · V06 34/34 · V07 12/12 · V08 25/25 · V09 2/2 · V10 2/2 · V11 1/1.

**How to read 100%.** The rules catch *the error classes we already knew about*, because both error sources are
produced by this project. It says nothing yet about the unusual mistakes of a real model. An earlier run reported one
false alarm; the "correct" case (AOV split by payment type) really did fan out, so the bug was in the test generator,
which was fixed.

## 2. Verifier vs. LLM-as-judge (simulated)

Same 202 cases, 3 runs each. The judge is the mock model asked "is this SQL correct for the metric?", with noise
calibrated to look like a typical judge.

| Checker | Recall | False alarms | Same verdict across 3 runs | Cost / case | Latency |
|---|---|---|---|---|---|
| Lineage verifier | 100.0% | 0.0% | 100% | 0 USD | 12 ms |
| Judge mock-large | 64.8% | 8.3% | 74.8% | 0.00063 USD | ~1.8 s |
| Judge mock-small | 60.3% | 23.9% | 48.5% | 0.00004 USD | ~0.7 s |

The verifier columns are measured; the judge columns are only as meaningful as the mock's noise model. The point the
table is built to test with a real model: a deterministic checker is stable run to run and can say *why*.

## 3. Agent by model and configuration (mock)

**Benchmark**: 116 Vietnamese questions (`backend/eval/benchmark.json`, generated by `python -m lvda.benchmark`):
12 metrics × 9 templates (plain, month, quarter, year, by state, by state without diacritics, by month, by payment
type, top-5 categories), 9 out-of-scope questions and 4 definition questions. Each has a category, difficulty, the
traps it targets and canonical SQL.

Configurations: **A** schema only · **B** + metric and verified-query retrieval · **C** + verifier labels (red is held)
· **D** + self-fix (≤ 2 rounds).

| Model | Config | Correct | Wrong, flagged | Held | Wrong, silent | Accuracy | Avg cost / question |
|---|---|---|---|---|---|---|---|
| mock-large | A | 45 | 0 | 0 | 71 | 38.8% | 0.00177 USD |
| mock-large | B | 108 | 0 | 0 | 8 | 93.1% | 0.00197 USD |
| mock-large | C | 108 | 0 | 8 | 0 | 93.1% | 0.00193 USD |
| mock-large | D | 116 | 0 | 0 | 0 | 100.0% | 0.00213 USD |
| mock-small | A | 36 | 0 | 0 | 80 | 31.0% | 0.00012 USD |
| mock-small | B | 67 | 0 | 0 | 49 | 57.8% | 0.00013 USD |
| mock-small | C | 66 | 9 | 41 | 0 | 56.9% | 0.00012 USD |
| mock-small | D | 106 | 9 | 0 | 1 | 91.4% | 0.00017 USD |

Out-of-scope questions refused correctly: 9/9 in every configuration. mock-small returns malformed JSON on some first
calls; the structured-output retry recovered all 13. Repeated runs hit the response cache (`eval/.cache/llm`).

**Why these are not results.** The mock's mistakes are injected and its fixes come from the same builder as the
canonical SQL, so D is close to perfect by construction. What the table does show is the *shape*: C stops nearly
all wrong numbers from reaching the user (silent wrong 80 → 0 for mock-small), and D turns most of the held answers
back into correct ones at ~1.5× the cost of A.

**First-attempt error taxonomy** (mock-small, D): V06 wrong aggregate 18 · V03 missing filter 17 · V08 wrong time
column 14 · V05 fan-out 10 · V02 wrong measure 9 · V07 wrong key 9.

## 4. Understanding and retrieval

| Measure | Result | Set |
|---|---|---|
| Intent classification (AGT-01) | 48/50 = 96.0% | `backend/eval/intent_set.json`, labelled by hand |
| Metric matching (MET-04) | 40/42 = 95.2% | same set, questions that name a metric |
| Table retrieval recall@5 (AGT-02) | 100% | benchmark questions, BM25 over tables, columns, descriptions, metrics |

Both intent misses are paraphrases the rule-based interpreter does not know ("khách đã trả tổng cộng…", "mất bao
nhiêu ngày giao hàng…"); a real model should handle them. Retrieval recall is inflated: once a metric is matched its
tables are boosted, and benchmark questions are generated from the metric names. Treat it as a regression check.

## 5. Limitations

- No real LLM: model comparisons, the judge baseline and source (b) must be rerun against real models, with source (b)
  labelled by a person.
- Synthetic data: row counts and distributions follow the Olist schema, not the real dataset. Load the Kaggle CSVs
  with `python -m lvda.seed.bootstrap --reset --olist-dir <path>` and rerun.
- Single dialect (Postgres) and a single warehouse per database entry.
